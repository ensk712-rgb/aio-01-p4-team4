**Error Workflow 설명:** 현재 `ticketmoa-errors` 연결은 support·agents·refund·payment·handoff·ops 6개다. search·tech·index에는 설정이 없다. 예상 API/LLM 장애는 각 하위 오류 경로에서 처리하므로 WF-04 통과를 Error Trigger 발화 시험으로 대체하지 않는다. Discord의 WF-04·WF-12 수신은 확인했지만 예상 밖 실행 오류 → Error Workflow → 알림의 VM 실측은 남아 있다.

**후속 반영 · Error Workflow 배포와 격리 검증:** 위 문장은 당시 미검증 상태의 기록이다. `ticketmoa-errors` (`ticketmoaErrors01`)는 기존 **4개 → 최신 9개 노드**로 운영 n8n 배포를 마쳤고 배포 후 `active: true`, Support·handoff 활성 상태를 확인했다. 배포 전 SHA-256 일치 및 `flow.py check` 통과, 기존 운영본 백업은 `backups/ticketmoa-errors-before-update.json`, 배포 소스 커밋은 `9254bff`다. Error Trigger 오류 수신, 허용 목록 기반 민감정보 제외·정규화, 실행 ID 기반 중복 알림 억제, `/alerts`·Discord 독립 알림, 캐시 장애 시 알림 계속 처리, Error Workflow 자체 재귀 방지가 구현됐다. 동시 실행의 원자적 중복 차단은 보장되지 않는다.

격리 n8n **2.42.6**의 시험용 Support `ticketmoaE2ESupport`에서 미처리 오류 실행 **10**이 실패했고 Error Workflow 실행 **11**이 자동 실행됐다. 모의 `/alerts`·Discord가 모두 알림을 받았고 시험용 질문·전화번호·토큰은 포함되지 않았다. 관련 단위 테스트 **6/6** 통과 후 로컬 시험 컨테이너를 종료했다. 모의 수신 기록 주소 `http://127.0.0.1:18800/events`는 격리 시험 전용이며 운영 웹앱 주소나 운영 설정이 아니다. 운영 웹앱은 `https://aio-t4.isitsoft.kr/`이다. **운영 Support 오류 주입 자동 실행, 운영 Discord 실제 수신, 동시 실행 원자적 중복 차단은 미검증**이다.

### QR·앱 문의 경로와 시간 예산 (11/06 정적 확인)

WF-01은 `support` 사용자 권한 조회·입력 검사 → `agents` 분류 → `search` 고객용 근거 검색 → `tech` 작성 → `agents-verify` 검증 → 응답 조립·로그·최종 응답 순서다. 정상 경로의 LLM 호출은 분류·작성·검증 3회다. QR 질문의 정답 문서는 `mobile-ticket-troubleshooting`, 앱 로그인 질문은 `app-login-troubleshooting`이다.

`timings.total_ms`는 사용자 조회 뒤 `Check input`에서 시작해 `Build response`에서 끝난다. 따라서 사용자 조회·그 앞 실행과 응답 조립 뒤 로그 전송·최종 응답 구간은 포함하지 않는다. 시험의 HTTP 왕복 시간과 차이가 나도 그 차이를 곧바로 네트워크 지연이라고 단정하지 않는다.

### LLM·검증 장애의 사유 보존 점검

**미통과.** 현재 tech·support Code 노드 원문을 Windows Node에서 그대로 실행해 오류 입력 3종과 무근거 대조 입력을 재현했다. VM Credential이나 워크플로우는 변경하지 않았다. 이번 검사는 Code 노드 재현이며 새 VM 장애 주입 시험은 아니다.

| 입력 | 최종 route / reason | 로그 status | 발견 |
| --- | --- | --- | --- |
| 작성 LLM 오류 | 담당자 이관 / `llm_unavailable` | **success** | 장애를 성공 로그로 기록 |
| 검증 Agent LLM 오류 | 담당자 이관 / `verification_failed` | error | tech의 `issues: [llm_unavailable]`이 support에서 사라짐 |
| 검증 HTTP timeout | 담당자 이관 / `verification_timeout` | **success** | 장애를 성공 로그로 기록 |
| 실제 근거 없음 대조 | 담당자 이관 / `no_evidence` | success | 위 장애 응답과 reason은 구별됨 |

응답 route는 세 장애 모두 이관이며 `no_evidence`나 자동 답변으로 바뀌지 않는다. 그러나 support `Log record`는 reason이 `_failed`로 끝나거나 `agents.error` 등이 있을 때만 error로 기록한다. 따라서 `llm_unavailable`·`verification_timeout`을 놓친다. 또한 `Collect tech`가 하위 `issues`를 보존하지 않아 검증 모델 장애와 근거·정책 검증 불통과의 세부 구분이 최종 응답·로그에서 소실된다. 현재 `buildLog` 결과에는 reason도 포함되지 않는다.

필요한 수정: A 담당 support에서 장애 사유를 명시적으로 분류해 로그에 보존하고, C 담당 tech의 검증 `issues`를 support까지 전달해 운영 장애와 답변 품질 불통과를 구별해야 한다. 근거 없음·정상 이관을 일괄 장애로 바꾸지 않는다. 수정 후 세 장애와 무근거 대조 경로를 다시 확인해야 이 체크를 완료할 수 있다. 이번에는 문제 확인과 기록만 했으며 워크플로우·공통 함수는 수정하지 않았다.

#### 로컬 수정 및 회귀 검사 완료

사용자의 수정 요청에 따라 A 담당 support와 공통 로그 함수를 수정했다. `lib/common.js`의 `classifyOutcome`을 `buildLog`에서 사용하고 같은 함수 원문을 support Code 노드에 복사했다. 작성 LLM 장애·검증 timeout은 `status=error`와 사유 코드를 남긴다. 검증 `issues`는 `agents.verification_issues`로 최종 응답과 로그에 보존한다. `failure_kind`로 dependency·model_output·verification_rejected·verification_unknown·no_evidence를 구별하며, 임의 오류 원문 대신 사유 코드만 로그에 남긴다. 실제 무근거·정상 이관을 일괄 오류로 기록하지 않는다. B·C 워크플로우와 공통 응답 최상위 계약은 변경하지 않았다.

공통·환불 안전장치·실제 tech→support 응답 조립→로그 Code 연결 회귀 검사 **38/38 통과**. 작성 오류, 검증 LLM 오류, 검증 timeout은 모두 이관과 error 로그이고 검증 장애 세부 사유도 유지된다. 검증 품질 거절과 실제 무근거 대조도 함께 검사했다. `flow.py check`는 오류 없이 통과했으며 기존 Code 문자열 경고 2개만 남는다. **로컬 수정 완료이며 VM 배포·장애 주입·전체 common 재시험은 아직 수행하지 않았다.** VM 운영상의 체크 완료는 반영 후 확인해야 한다.

### 11/06 추가 확인: 제한 변경 후 지연·권한·중복
