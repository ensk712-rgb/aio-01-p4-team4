## 2. 전처리·청킹

`ticketmoa-index`는 Webhook의 `documents: [{doc, text}]` 배열을 받아 문서별 Markdown 구조를 검사하고 `##` 제목부터 다음 `##` 제목 직전까지를 한 청크로 만든다. 청크 본문에 문서명·절 제목을 포함하고 `doc`, `section`, `access_level` 메타데이터를 부여한다. **Overlap = 0**이다.

| 방식 / 평가 환경 | 단위·설정 | 청크 수 | 청크 길이 최소/중앙/최대 | hit@3 |
|---|---|---:|---|---:|
| 정제본, 로컬 n8n (기존 35문항) | `##` 절, overlap 0; positive 28개, Q11 원래 1절 | **42** | **116 / 229 / 432자** | **27/28 (96.4%)** |

| 기존 문서, 로컬 n8n (비교용) | `##` 절, overlap 0 | 33 | 116 / 194 / 379자 | 26/28 (92.9%) |

**비교 해석 주의:** 기존 문서에서 틀린 Q04는 정답 절이 정제본에 새로 생긴 문항이다. 그러므로 **26/28 → 27/28 차이를 공정한 품질 향상 효과로 주장할 수 없다**. 동등한 정답 조건의 재평가가 필요하다. 이 표는 VM 결과가 아니다.

**`hit@3`(히트 앳 쓰리)**: 정답 `doc`과 허용된 정확한 `section`이 검색 상위 3개 중 하나에 함께 있으면 성공(1)으로 센다. 직원 문서 누출과 근거 없는 질문은 정상 질문 hit@3 분모에서 제외한다. 로컬 n8n 기존 35문항은 27/28, 수정 38문항은 Q11의 허용 절을 넓힌 기준으로 30/30이다. 질문 구성과 Q11 채점 조건이 달라 두 값의 차이를 성능 향상으로 해석하지 않는다. 로컬 Python A/B도 수정 38문항의 확대 Q11 조건이며, B는 청크 안에 포함된 원문 절을 인정하는 더 넓은 판정이다. 모두 검색 결과 평가이고 생성 답변 평가는 별도다.

### 2.2 색인 전 정제·품질 기준

1. 문서 제목·`access_level`·`##` 절의 유효성, 빈 절, 연락처처럼 부적절한 형식의 예시를 점검한다.
2. `knowledge/`에는 **고객에게 답해도 되는 운영·안전 안내만** 남긴다. 공식 URL, AI 생성 경위, 개발·테스트·RAG 인덱스 설정 등의 설명은 본 설계서에 보존한다.
3. `doc`, `section`, `access_level` 메타데이터를 확인한다. 고객용 7개와 직원용 1개의 저장 대상이 섞이지 않아야 한다.
4. 환불 표가 분리·누락되지 않았는지, 긴급 입장 순서와 상담원 이관 조건이 유지됐는지 확인한다.
5. 변경 전후 `git diff`·파일 해시·색인 실행 ID를 기록하고, 정제 후 질문 목록으로 검색 평가를 반복한다.

**고객 답변에 사용해서는 안 되는 표현의 예:** '테스트 시나리오에서는', '가상 기준', '공식 자료 참고', '이 문서는 AI로 작성됨', 타 예매업체 URL. **남겨야 할 안전 지침:** 본인 확인 없는 타인 정보 조회 금지, 챗봇의 결제 취소·보상 약속 금지, 캡처 QR 대체 입장 금지, 직원 승인 절차 비공개, 근거 불충분 시 상담원 이관.

### 3.1 임베딩 모델 선택 이유

`text-embedding-3-large`를 선택한 이유는 고객의 표현과 문서 용어가 달라도 **문장 의미에 따라 관련 절을 검색**하려는 목적 때문이다. 예를 들어 'QR이 안 떠요'와 '모바일티켓 표시 오류'를 의미적으로 연결하는 검색에 적합하다. 또한 현재 팀의 n8n/OpenAI 노드로 설정할 수 있고, 기본 3,072차원 임베딩을 제공한다.

다만 이 모델이 다른 모델보다 이번 데이터에서 실제로 더 정확하다는 **비교 실험 결과는 아직 없다**. 선택은 활용 가능성과 검색 품질을 고려한 설계 판단이며, 비용·응답 시간·`hit@3` 비교를 통해 적합성을 사후 검증한다.

## 4. 인덱스·메타데이터

색인과 검색은 n8n In-Memory Vector Store를 사용한다. 현재 논리 인덱스는 두 개다.

| 권한 | 고정 Memory Key | `clearStore` | 저장 메타데이터 |
|---|---|---:|---|
| 고객용 | `ticketmoa_kb_v1_all` | `true` | `{doc, section, access_level: "all"}` |
| 직원 전용 | `ticketmoa_kb_v1_staff` | `true` | `{doc, section, access_level: "staff"}` |

일반 요청은 `ticketmoa_kb_v1_all`만 검색한다. 현재 Search는 `search_staff: false`로 고정하며 `access_level: staff` 요청은 검색어를 비운 뒤 `staff_search_disabled`를 반환한다. 따라서 직원 저장소 검색은 현재 차단되어 있고, 직원 저장소 노드가 구성돼 있다는 사실만으로 검색 가능하다고 볼 수 없다. 요청의 `access_level`은 인증된 직원 권한의 증거가 아니다. 현재 `scope`는 검색 결과를 받은 뒤 최대 100개 안에서 필터링하므로, 결과 수가 커지면 해당 문서가 상위 100개 밖에 있어 scope 결과가 누락될 수 있다.

다음 구현 위험은 로컬 검색 평가와 별개로 최종 배포/실패 상황에서 추가 검증이 필요하다.

- 로컬에서 42청크를 색인하고 38문항을 검색했다. 정답 절을 맞힌 결과로 보아 `doc`·`section`이 첫 항목으로 반복되지는 않았다. 2026-11-06 VM에서는 8개 문서·42청크 재색인과 고객·직원 검색 복구를 확인했지만, **42개 청크 전체의 실제 저장 본문·메타데이터 일치 여부는 미검증**이다. 현재 VM의 활성 index/search 설정은 저장소본과 대조해 일치했으며, 이는 실행 당시 저장된 청크 내용을 증명하지 않는다.
- **VM 예상 청크 명세 확인 (2026-11-06):** 원본 Markdown 8개(일반 7, 직원 1)에서 일반 예상 청크 37개·직원 예상 청크 5개·전체 42개를 만들었고, 예상 명세의 빈 청크는 0개였다. 예상 청크 길이는 116~432자이며, 각 청크의 `doc`, `section`, `access_level`, 본문 SHA-256 명세 생성을 확인했다. 이는 원본 문서에서 계산한 **예상 입력 명세**이며 실제 Simple Vector Store 저장 레코드의 전수 검증 결과가 아니다.
- `Build result`의 문서·청크 수는 검증 단계 값이며, Vector Store에 실제 저장된 수가 아니다. 두 Store 분기의 완료를 합쳐 한 번만 응답하는지와 저장 실패 수 집계도 미검증이다.
- **청크 본문 생성 수정 (현재 checkout):** `ticketmoa-index`의 본문 템플릿은 실제 줄바꿈을 생성하도록 수정했다. 과거 n8n 실측 116/229/432자와 검색 평가는 당시 버전 결과로 보존하며, 수정본은 로컬 예상 입력의 단위 테스트에서 공개 37·직원 5·총 42개를 확인한다.
- `tools/verify_rag_store.py`는 원본 문서에서 예상 본문과 `doc`·`section`·`access_level`을 만들고, 양쪽 저장소의 읽기 전용 스냅샷과 비교한다. `exhaustive` 표식·실제 총수·필수 필드가 없거나 일부 반환이면 `UNVERIFIABLE`로 끝낸다. 현재 저장소에는 실제 인메모리 레코드를 추출해 완전성을 증명하는 경로가 없으므로, 이 도구만으로 운영 데이터 전수 검증이 완료되지는 않는다. Search 직원 차단은 유지한다.
- `clearStore: true`는 색인 시 기존 Memory Key를 지운다. 새 색인이 완전히 성공하기 전에 실패하면 기존 인덱스 대신 비었거나 일부만 저장된 상태가 될 수 있다.


### 4.1 고객·직원 검색 권한과 검색 신뢰성

- **현재 비로그인 시연 정책:** 공개 고객 요청은 `ticketmoa_kb_v1_all`만 검색한다. 현재 공개 시연 범위에서는 Search가 fail-closed로 직원 전용 검색을 차단하며 일반 직원 요청도 검색하지 않는다. 로그인·사용자 인증은 현재 프로젝트 범위에서 구현하지 않는다. 질문의 이름·`user_id`·`access_level` 또는 서비스용 `X-Team-Key`는 직원 신원을 증명하지 않는다.
- **범위와 향후 확장:** 문서별 `all`/`staff` 분리와 두 저장소 구조는 구현돼 있지만, 직원 저장소 검색은 현재 제공 기능이 아니다. [인증 기술 설계서](AUTH-TECH-DESIGN.md)는 이전의 상용화 확장 제안이며 현재 작업의 미완료 요구사항으로 해석하지 않는다. 향후 별도 범위에서 직원 검색을 허용하려면 먼저 인증된 신원과 신뢰 경계를 구현하고 권한 시험을 통과해야 한다. 현재 차단 정책은 유지한다.
- 직원용 문서는 고객 검색 결과·답변 인용·LLM 문맥·로그에 나오지 않아야 한다. **로컬 38문항 평가의 고객 권한 검색에서 스태프 문서 노출은 0건**이었다.
- 2026-11-06 VM WF-05 시험에서도 고객용 검색만 실행되고 스태프 문서는 노출되지 않았다. 한 회차는 검증 issue `not_relevant`로 담당자 이관됐으며, 다른 회차는 `writer_staff_only_terms`로 이관됐다. 이는 명시적인 `권한 없음` 거절 결과가 아니다. 검색 전 `access_level=all`, `search_staff=false`, 고객용 Memory Key 사용과 스태프 검색 미실행이 확인된 것을 권한 분리 근거로 기록한다 (`runs/vm/ticket-evidence-common-20261106-034042.json`).

## 5. 백업·복구·확장

**이번 프로젝트의 구현 범위:** n8n 기반 AI 기술지원의 공개 RAG 검색과 시연 운영을 목표로 하며, 기존 `ticketmoa-index`·`ticketmoa-search` 및 In-Memory Vector Store를 유지한다. 원본 8문서에서 계산한 예상 청크는 공개 37개·직원 5개·총 42개다. 현재 공개 시연 범위에서 직원 검색은 fail-closed로 차단한다. PostgreSQL/pgvector 같은 영속 저장소 도입은 이번 범위에 포함하지 않는다. 실제 저장 레코드 42개 전수 일치, 원자적 인덱스 교체, 자동 롤백, n8n 재시작 후 색인 자동 보존은 **구현·검증 완료가 아니며 향후 상용화 개선 과제**다.

백업 원본은 Git으로 버전 관리하는 `knowledge/*.md` 파일이다. 현재 별도의 벡터 인덱스 백업·스냅샷·원자적 교체 절차는 구현되어 있지 않다. n8n의 Simple Vector Store 문서는 저장소가 앱 메모리에 있으며 재시작 시 데이터가 사라지고 메모리 압박 때 정리될 수 있다고 설명한다. 메모리 키는 워크플로우별로 격리되지 않고 인스턴스 사용자 사이에서 공유된다. 따라서 재시작 유지성은 보장하지 않으며, 운영 서버의 실제 설정·동작도 별도로 확인해야 한다. ### 5.3 재시작 후 재색인·권한 검색 복구 절차

In-Memory Vector Store는 n8n 재시작 뒤 데이터가 사라질 수 있으므로, 재시작 또는 워크플로우 배포 후 승인된 `knowledge/*.md` 8개를 다시 색인한다. 2026-11-06 최종 VM 재검증에서는 n8n 재시작 후 8개 문서·42청크를 재색인하고 고객/스태프 검색을 확인했다 (`docs/daily/DAY80.md`, `runs/vm/wf01-fix-metadata-20261106-025239.json`). 이 결과는 당시 배포 버전의 실측 기록이며, 현재 임시 보안 패치에서 직원 검색이 가능하다는 뜻이나 재시작 후 영구 보존을 뜻하지 않는다. 다음 실행 시 VM에는 승인된 문서 커밋과 `ticketmoa-index`·`ticketmoa-search` 워크플로우가 준비되어 있어야 한다. 배포 시간은 공용 서버 사용자와 조율한다.

**현재 운영 제한 (2026-11-07 기록 기준):** Search는 공개 시연 범위의 fail-closed 정책으로 정상 직원 요청을 포함해 직원 검색을 차단한다(4.1절). 사용자 로그인·인증은 이번 프로젝트의 필수 개발 범위가 아니며, 이를 구현 대기 항목으로 삼아 직원 검색을 복구하지 않는다. `access_level: staff`를 직접 지정하는 것도 권한 근거가 아니다. 현재 `tools/reindex.py`는 직원 검색을 호출하지 않고 공개 검색과 직원 문서 비노출만 검사한다. 이 상태는 보관된 11/07 실행 기록에 근거하며, 현재 VM에 직접 접속해 확인한 것은 아니다.

시연 운영 절차는 다음 순서다. **1)** 승인된 원본 문서 버전을 확인하고 `python3 tools/verify_rag_store.py --check-sources`를 저장소 루트에서 실행해 8문서(공개 7·직원 1), 예상 42청크(공개 37·직원 5), 중복·빈 절 없음을 확인한다. 이 명령은 읽기 전용이며 `PASS`는 **원본 입력에만** 적용된다. **2)** 운영 담당자가 실행 시점을 조율한 뒤에만 아래 재색인 명령을 실행한다. 두 Memory Key의 `clearStore: true`로 기존 데이터가 먼저 지워지므로 실패 시 공개·직원 저장소가 비거나 일부만 채워질 수 있다. **3)** 색인 응답의 문서·청크 수, `issues: []`, `store_output_received`와 도구의 공개 검색·직원 문서 비노출 결과를 확인한다. 출력 청크 수는 저장 전 수량이다. **4)** 색인이나 공개 검색이 실패하면 성공으로 표시하지 않고 원본 문서·n8n 상태·오류를 확인한 뒤, 승인된 문서 전체로 수동 재색인하고 공개 검색을 다시 확인한다. 이전 인덱스로 자동 복원되지는 않는다. **5)** n8n 재시작 후에는 색인 상태와 공개 검색을 먼저 확인하고 필요하면 같은 사전 점검·수동 재색인을 반복한다. 모든 단계에서 직원 검색 차단을 유지한다.

```bash
ssh aio-t4 "bash -lc 'cd ~/aio-01-p4-team4 && uv run --env-file .env tools/reindex.py'"
```

현재 `tools/reindex.py`는 `knowledge/*.md`를 `ticketmoa-index`에 보내고 `ticketmoa-search`에 **`access_level: all`만** 보내 공개 QR 검색과 직원 전용 표현 비노출을 확인한다. 종료 코드 0은 공개 검색 점검 통과를 뜻하며 직원 저장소의 실제 저장 레코드 전수 일치나 자동 복구를 뜻하지 않는다. 임베딩 API를 호출하므로 실행 전 비용과 시점을 확인한다. 다음 수량은 색인 출력 대조 기준이며, 직원 검색 성공 출력은 과거 실측 기록이다.

- 문서 **8/8**, 일반 **7**, 직원 **1**
- `##` 청크 **42개**, `issues` 없음, 색인 결과 `store_output_received`
- 당시 버전의 실제 재색인 도구 출력(현재 패치의 성공 기대값 아님): `검색 확인: 일반 색인 True, 스태프 색인 True, 결과 3건`. 코드의 응답 필드는 `indexed`, `staff_indexed`, `hits`이며 결과 건수는 `len(hits)`로 출력한다 (`tools/reindex.py`, `workflows/ticketmoa-search.json`).

별도 `--check-sources` 사전 점검은 예상 문서·청크 수가 다르면 실패한다. `reindex.py` 자체의 색인 응답 확인은 실제 저장 레코드를 세지 못하므로 두 결과를 구분한다.

권한별 검색과 저장 데이터 검토는 다음 제한을 따른다.

1. **직원 검색은 현재 기능 범위에서 제공하지 않는다.** 과거에는 `ticketmoa-search`에 `access_level: staff`와 직원 전용 절을 겨냥한 검색어를 보내 두 저장소에서 `staff-entry-manual`의 기대 `doc`·`section`이 검색되는지 확인했다. 현재는 fail-closed 정책으로 차단된다. 이 프로젝트에서는 직원 검색 성공 시험이나 인증 기능 구현이 완료 조건이 아니다. 향후 프로젝트 범위가 별도로 바뀌면 신뢰된 호출 경계·권한 정책·배포 전환을 새로 승인하고 시험한다. 요청 본문의 `access_level: staff`만으로 직접 검색하는 절차를 재사용하지 않는다.
2. 일반 고객 계정으로 기존 `WF-05 권한 없는 문서`를 실행한다. `staff-entry-manual`, `책임자 코드`, `수기 모드`가 `sources`와 답변에 나오지 않아야 한다. 이 확인은 저장소에 있는 `cases/common.json`의 기대 조건을 사용한다.
3. n8n의 성공한 색인 실행 상세에서 `Validate and make chunks`의 42개 출력과 Loader 입력을 확인한다. 이는 저장 전 예상 입력의 증거이지 Vector Store 실제 저장 데이터의 증거는 아니다. 워크플로우 JSON에는 Loader의 본문·메타데이터 표현식이 각 chunk의 `$json.text`·`$json.doc`·`$json.section`·`$json.access_level`을 참조하도록 적혀 있지만, Default Data Loader는 LangChain sub-node다. n8n은 sub-node 표현식이 여러 입력 item을 item별로 반복 평가하지 않고 첫 item 기준으로 해석된다고 설명한다. 따라서 42개를 일괄 전달하는 이 구조에서 실제 본문·메타데이터가 chunk별로 보존된다고 코드 표현식만으로 단정할 수 없다. 이 항목은 실제 Loader/저장 데이터 검증의 핵심 위험이다. [n8n sub-node 표현식 동작](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.vectorstoreinmemory/)
4. 실제 저장 레코드 42개 전수 대조는 현재 구조에서 **미지원·미검증**이다. Simple Vector Store의 Get Many는 질의 기반 top-N 결과이며 전체 저장소 열거를 증명하지 못한다. `tools/verify_rag_store.py`도 완전한 읽기 전용 스냅샷을 얻지 못하면 `UNVERIFIABLE`로 판정한다. 검색 결과를 반복 수집해 전수 일치로 표시하지 않는다.
5. 저장 데이터 전수 검증, 원자적 교체, 자동 롤백, 재시작 후 자동 보존은 이번 시연 범위 밖의 상용화 개선 과제다. 현재 복구는 승인된 Git 원본 문서의 **전체 수동 재색인과 공개 검색 재확인**에 의존한다.
예상 청크 명세를 다시 만들 때는 아래 읽기 전용 명령으로 각 Markdown의 문서명·절·권한과 본문 해시를 출력할 수 있다. 이 명세는 색인 코드에서 기대하는 입력을 재구성할 뿐, Vector Store에 실제 저장된 데이터의 증거는 아니다. 실행 결과가 8문서·일반 37청크·직원 5청크·총 42청크인지 먼저 확인한다.
```bash
cd /home/toor/aio-01-p4-team4
python3 - <<'PY'
from pathlib import Path
import hashlib, re
rows=[]
for path in sorted(Path('knowledge').glob('*.md')):
    text=path.read_text(encoding='utf-8')
    m=re.search(r'^>\s*access_level:\s*(all|staff)\b', text, re.I|re.M)
    sections=list(re.finditer(r'^##\s+(.+)\s*$', text, re.M))
    if not m or len(sections)<3:
        raise SystemExit(f'invalid document: {path.name}')
    for i, heading in enumerate(sections):
        end=sections[i+1].start() if i+1<len(sections) else len(text)
        body=text[heading.end():end].strip()
        if not body:
            raise SystemExit(f'empty section: {path.stem} / {heading.group(1).strip()}')
        section=heading.group(1).strip()
        chunk=f'# {path.stem}\n## {section}\n{body}'
        rows.append((path.stem, section, m.group(1).lower(), len(chunk), hashlib.sha256(chunk.encode()).hexdigest()))
for row in rows:
    print('\t'.join(map(str,row)))
public=sum(r[2]=='all' for r in rows)
staff=sum(r[2]=='staff' for r in rows)
print(f'EXPECTED_ONLY docs={len(list(Path("knowledge").glob("*.md")))} public_chunks={public} staff_chunks={staff} total_chunks={len(rows)}')
if (public,staff,len(rows))!=(37,5,42):
    raise SystemExit('expected chunk manifest does not match 37/5/42')
PY
```
