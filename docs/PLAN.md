## 개요

가상의 티켓 예매 플랫폼 티켓모아의 고객 기술 문의를 업무 유형별로 자동 분류하고, 공개 지식 문서(RAG)로 해결 방법을 안내하며, 판단이 필요하거나 개인정보 없이 이관할 수 있는 건은 맥락을 요약해 상담원에게 티켓으로 넘기는 멀티에이전트 기술지원 워크플로우를 n8n으로 구축한다. 예매별 문의·환불·결제 조회는 현재 제공 범위에 포함하지 않는다.

**목표 문장 (주제 한 줄)**

> 온라인 티켓 예매 플랫폼 티켓모아의 예매 고객을 위한 모바일티켓·결제·입장 기술지원 자동화

> 온라인 티켓 예매 플랫폼을 운영하는 가상의 기업 티켓모아의 고객센터를 대상으로, 모바일티켓·앱·결제 오류·입장 장애 같은 고객 기술 문의를 자동 분류하고 공개 RAG 지식 검색으로 안내하며, 해결이 어렵거나 개인정보 없이 이관할 수 있는 건은 요약해 상담원에게 티켓으로 넘기는 멀티에이전트 기술지원 워크플로우를 구축한다. 입장 장애 시에는 승인된 공개 대체 입장 방법을 안내한다. 예매별 문의·환불·결제 상태 조회는 현재 시연 범위에서 제공하지 않는다.

### 현재 시연 범위 (2026-11-07 구현 기준)

회원가입·로그인·세션·사용자 인증은 구현하지 않는다. 공개 기술지원, FAQ/RAG 검색, 상담원 이관에 더해 본인 문의 조회와 환불 2단계를 제공한다. 로그인이 없어 요청의 `user`는 본인 확인이 아니다. 기록의 `requester`와 일치해야 조회되므로 내 이름으로 남의 건은 볼 수 없지만, 다른 사람 이름을 입력하는 사칭은 막지 못한다. 데이터는 모두 가짜이고 연락처는 가려서 답한다. 직원 전용 RAG 검색은 공개 경로에서 차단 상태를 유지한다. 11/06 비로그인 일괄 차단은 공통 WF-07·WF-11과 충돌해 11/07 팀 결정으로 되돌렸다.

현행 범위와 실제 검증은 `docs/EXECUTION-RESULT.md`에서 회차별로 구분한다.

**핵심 원칙**

-   아키텍처는 도메인 중립, 데모는 티켓 플랫폼 한 곳에서 깊게
-   기술 문의는 지식 문서를 근거로 끝까지 안내하고, 근거가 없으면 추측하지 않고 이관
-   공개 정책·기술 문의는 자동 안내 또는 상담원 이관. 예매·환불·결제 처리는 본인 건만, 실제 취소는 상담원
-   환불은 2단계 고객 확인 후 티켓 생성
-   장애 상황에서도 관람이 끊기지 않도록 대체 입장 방법을 우선 안내

## 기존 기획 대비 변경점 (초기 기획 이력)

아래 비교표와 초기 업무 분류·데모·MVP 표는 기획 당시의 요구사항 기록이다. 현재 동작은 위 시연 범위와 실행 결과서를 따른다.

| 항목 | 기존 기획 (CultureCare) | 변경 기획 (티켓모아) |
| --- | --- | --- |
| 대상 | 디지털 전시 솔루션 B2B 고객 시설 | 티켓 예매 플랫폼의 예매 고객 (기업 고객센터의 기술지원) |
| 문의 범위 | 기술 장애 문의 | 모바일티켓·앱·결제 오류·입장 장애 중심, 예매 조회·환불 안내·일반 정보 포함 |
| 처리 방식 | RAG로 해결 방법 안내 | RAG 안내 + 예매 조회 + 고객 확인 후 요청 접수 |
| 이관 | 미해결 시 기술지원 담당자 | 업무별 이관 조건 + 맥락 요약 핸드오프 |
| 확장성 | 단일 도메인 고정 | 업무 레지스트리로 업무·도메인 추가 |
| 유지되는 강점 | 장애 시 대체 관람 방법 제공 | 기술 장애 업무의 "대체 입장 안내"로 계승 |

**해결하려는 문제**

-   티켓 플랫폼 상담은 오픈·공연 직전에 문의가 몰리고, 대부분 반복 기술 문의(QR이 안 떠요, 결제가 됐는데 예매가 없어요, 로그인이 안 돼요)다.
-   공연 직전 입장 장애는 해결보다 입장이 먼저인데, 단순 FAQ 챗봇은 대체 입장 방법을 바로 주지 못한다.
-   이관될 때 맥락이 전달되지 않아 고객이 같은 설명을 반복한다.

## 사용자와 채널

과제 채점과 같은 **공통 Webhook 계약**을 기본 입력으로 둔다. 웹 채팅 위젯과 Slack은 이 Webhook을 부르거나 결과를 받는 가산 채널이다.

| 사용자 | 하는 일 | 기본 (필수) | 가산 (선택) |
| --- | --- | --- | --- |
| 고객 | 공개 기술 문의, FAQ/RAG, 일반 정책 안내 | `POST /webhook/ticketmoa-support` | 웹 채팅 위젯 (예시 화면 ①②). 개인 예매·문의·환불 상태 조회는 미제공 |
| 상담원 | 이관 건 처리, 환불 승인 | `POST /tickets` 티켓 + `POST /alerts` 알림 | 실제 Slack 알림, 상담원 콘솔 (예시 화면 ③) |
| 현장 스태프 | 입장 장애 대응 | `POST /alerts` (긴급) | 실제 Slack 긴급 채널 |
| 운영 관리자 | 레지스트리·지식 문서 관리, 지표 확인 | `knowledge/`, 레지스트리 JSON, `runs/` | 대시보드 |

**요청·응답 (공통 계약, 바꾸지 않음)**

-   요청: `{"request_id", "user", "channel", "question", "attempt", "context"}`
-   응답: `{"request_id", "route", "answer", "sources", "ticket", "agents", "security", "timings", "reason"}`
-   `route`: `자동 답변` · `보완 질문` · `담당자 이관` · `권한 없음` · `차단`
-   잘못된 입력은 HTTP 400 `{"error": "invalid request", "codes": [...]}`

## 업무 분류 체계

아래 분류표는 초기 계획의 업무 목록이다. 현재는 공개 기술지원·정책 안내를 제공하고 개인 데이터 조회·개인별 환불 처리는 하지 않는다.

| 업무 유형 | 예시 문의 | 처리 방식 | 자동화 수준 | route |
| --- | --- | --- | --- | --- |
| 기술 장애 (입장) | 공연 10분 전인데 QR이 안 떠요 | 대체 입장 안내 → 트러블슈팅 RAG, 긴급 시 현장 알림 | 자동 + 긴급 시 이관·알림 | 자동 답변 / 담당자 이관 |
| 앱·계정 오류 | 로그인이 반복돼요, 인증 문자가 안 와요 | 앱 트러블슈팅 RAG | 자동 답변 | 자동 답변 |
| 결제 오류 | 결제됐는데 예매가 없어요, 이중결제 | 공개 결제 오류 안내 또는 개인정보 없는 이관. 예매·결제 기록 조회는 미제공 | 공개 안내 / 이관 | 자동 답변 / 담당자 이관 |
| 예매 조회 | 내 예매 상태 알려줘 | 본인 건 조회; 남의 건은 거절 | 조회 | 자동 답변 / 권한 없음 |
| 환불 안내·요청 | 일반 환불 규정 질문 / 예매별 취소액 질문 | 일반 정책은 공개 안내. 예매별 계산·상태·확정은 미제공 | 정책 안내 / 개인 요청 차단 | 자동 답변 / 권한 없음 |
| 일반 정보 | 주차, 입장 시간, 관람 연령 | FAQ·공연정보 RAG | 자동 답변 | 자동 답변 |
| 부정 예매 (매크로·해외 IP) | 매크로 의심으로 예매가 막혔어요, 해외에서 예매가 안 돼요 | 반복 요청·가상 IP 규칙으로 LLM 앞에서 차단, 문의에는 `fair-booking-policy` RAG로 제한 사유·해제 방법 안내 | 규칙 차단 + 자동 답변 | 차단 / 자동 답변 |
| 암표 신고 | 중고 사이트에서 웃돈 붙여 팔고 있어요 | 신고 접수 → 보안팀 티켓 | 항상 이관 | 담당자 이관 |
| 불만/VOC | 강한 부정 감정, 민원 | 감정 감지 → 요약 | 상담원 이관 | 담당자 이관 |
| 모호/기타 | 의도가 불분명한 문의 | 추가 질문 후 재분류 (최대 3회) | 3회째 이관 | 보완 질문 |

**분류 결과 스키마 (Supervisor 출력)**

```json
{
  "intents": ["refund_request"],
  "entities": { "booking_id": "T20261027-0412", "show_name": "뮤지컬 OOO" },
  "sentiment": "neutral",
  "urgency": "normal",
  "confidence": 0.91
}
```

intents를 배열로 두어 복합 문의를 순서대로 처리한다. confidence가 기준(예: 0.7) 미만이면 추가 질문으로 보낸다. 출력을 JSON으로 읽지 못하면 이관한다(fail-closed).

## 시스템 아키텍처

모든 메시지는 Webhook 하나로 들어와 입력 검사를 거친 뒤 Supervisor에서 분류되고, 추가 질문, 업무 처리, 상담원 이관 중 하나로 간다. 조회와 검색은 바로 실행하고, 환불처럼 확인이 필요한 요청은 두 번의 요청으로 나눈다.

![시스템 아키텍처](images/architecture.png)

업무 처리 중 해결이 안 되는 건도 상담원 이관으로 넘어가며, 모든 경로는 검증, 응답, 로그 저장으로 끝난다.

## 업무 레지스트리 (범용성 설계)

업무 정의를 코드에서 떼어 레지스트리 하나로 관리한다. 과제에서는 별도 DB 없이 **JSON 파일(또는 Code 노드의 설정)**로 두고, 새 업무는 항목 하나와 서브워크플로우 하나로 추가한다. 다른 산업에 적용할 때는 레지스트리·지식 문서·API 어댑터만 바꾼다.

| 필드 | 설명 | 예시 (환불 안내·요청) |
| --- | --- | --- |
| intent_id | 업무 식별자 | refund_request |
| description | Supervisor가 분류에 쓰는 설명 | 예매 취소 및 환불 요청 |
| examples | 분류용 예시 문장 | 취소할게요 / 환불 되나요 |
| required_slots | 처리에 필요한 정보 | booking_id |
| handler | 연결된 서브워크플로우 (Webhook 경로) | /webhook/ticketmoa-refund |
| automation | 자동화 수준 | confirm_then_ticket |
| escalate_if | 이관 조건 | 환불액 30만원 초과, 공연 당일, sentiment = angry |
| kb_scope | 검색할 지식 문서 범위 | refund_policy, show_info |

**동작 방식**

1.  워크플로우 시작 시 레지스트리를 읽어 Supervisor 프롬프트(업무 목록, 설명, 예시)를 만든다.
2.  분류된 intent의 handler(서브워크플로우의 Webhook 경로)를 HTTP Request로 호출한다.
3.  required_slots가 비어 있으면 `보완 질문`으로 먼저 묻는다.
4.  escalate_if에 걸리면 처리 전에 이관한다. 이관 조건 판단은 LLM이 아니라 규칙(If·Switch)으로 한다.

**도메인 교체 예시**: 쇼핑몰이면 refund_request는 그대로 두고 kb_scope를 반품정책으로, handler의 조회 대상을 주문 기록으로 바꾸고, show_info 대신 delivery_tracking 업무를 추가한다.

## n8n 워크플로우 구성

메인 워크플로우는 수신·검사·분류·라우팅·응답만 맡고, 업무 처리는 업무별 서브워크플로우로 분리한다. 서브워크플로우는 **각자의 Webhook 경로**(`/webhook/ticketmoa-tech`, `/webhook/ticketmoa-handoff` 등)로 부른다. Execute Workflow 노드는 n8n마다 워크플로우 ID가 달라 팀원끼리 JSON을 주고받으면 깨지기 때문이다. 부르는 쪽 HTTP Request에는 timeout과 오류 출력을 두고, 하위가 멈추면 메인이 정해진 답(이관)을 한다. 팀원은 서브워크플로우 파일 하나씩 맡아 팀 저장소(git)로 주고받는다.

**구현 스택 (과제 고정)**

| 구성 | 기본 (필수) | 가산 (선택) |
| --- | --- | --- |
| 워크플로우 | n8n 2.42.6 | |
| LLM | OpenAI gpt-4.1-mini | |
| 임베딩 | OpenAI text-embedding-3-large | |
| 벡터 저장소 | In-Memory Vector Store (`ticketmoa_kb_v1_all`, 관리자 문서는 `ticketmoa_kb_v1_staff`) | PGVector(Supabase) |
| 예매·사용자 데이터 | 연습용 데이터 API가 읽는 `data/records.json`, `data/users.json` | 실제 DB |
| 티켓·알림·로그·DLQ·캐시 | 데이터 API `POST /tickets`, `POST /alerts`, `POST /logs`, `POST /dlq`, `/cache` | Jira, 실제 Slack, Postgres |
| 지식 문서 | `knowledge/` (팀 작성 6개 이상) | Notion |

**메인 워크플로우 (ticketmoa-support)**

1.  Webhook(`POST /webhook/ticketmoa-support`, Header Auth)으로 메시지 수신
2.  입력 검사: 빈 질문·없는 사용자·501자 이상이면 400, 주입 문장은 LLM 전에 `차단`, 같은 `request_id`는 중복 처리
3.  맥락 읽기: 이전 대화·진행 중 업무·확인 대기 상태는 요청의 `context`로 받고, 필요하면 `/cache`에 둔다 (별도 세션 DB 없음)
4.  레지스트리 로드 → Supervisor(AI Agent + Structured Output Parser)로 분류
5.  Switch: confidence 미달 → 보완 질문 / 이관 조건 충족 → ticketmoa-handoff / 그 외 → 업무별 handler (기술·조회·환불, 복합 문의는 search와 payment 병렬)
6.  검증 에이전트로 답이 근거 안에 있는지 확인, 개인정보 가림
7.  공통 응답 JSON으로 Respond, `POST /logs`로 기록

**서브워크플로우**

**환불 2단계 확인**

| 단계 | 요청 | 처리 | 응답 |
| --- | --- | --- | --- |
| 1차 | "어제 예매한 거 취소할래요" + booking_id | 본인 건 조회 → 환불규정 RAG → 수수료 계산 | `자동 답변`: 환불 예정 금액과 "확정하시겠어요?" 안내. `context`에 대기 중 요청 정보 |
| 2차 | 같은 대화의 다음 요청, `context.confirm = true` | 금액 한도·공연 당일 규칙 확인 → `POST /tickets` (category: refund) | `담당자 이관`: "환불 요청이 접수됐고 상담원이 처리합니다" + ticket 번호 |
| 취소 | `context.confirm = false` | 아무것도 만들지 않음 | `자동 답변`: 취소되지 않았음을 안내 |

에이전트는 실제 취소·결제 취소를 직접 실행하지 않는다. 실제 취소 API까지 붙이는 것은 가산으로 두고, 설계서에 "운영이면 예매 시스템의 취소 API를 같은 자리에 연결"이라고 적는다.

## 가드레일과 이관 정책

공개 문서 검색과 정책 안내는 제공한다. 개인 기록 조회가 필요한 요청은 로그인·본인 확인이 없어 처리하지 않으며, 개인 정보를 조회·포함하지 않는 범위의 문의만 이관한다.

**가드레일**

-   로그인이 없어 본인 확인은 요청 `user`와 `requester` 일치까지만 한다. 실제 취소는 상담원이 처리한다
-   초기 설계의 금액 한도와 고객 확인 후 티켓 생성은 과거 기획 이력이며 현행 개인 환불 처리 기능이 아님
-   본인 확인: 요청의 `user`, `user_id`, `access_level` 및 공용 `X-Team-Key`만으로 소유권을 인정하지 않음
-   개인정보 마스킹: 응답·로그·상담원 요약에서 전화번호·이메일 마스킹
-   근거 없는 답변 차단: RAG 검색 결과가 없으면 추측하지 않고 이관

**이관 조건**

-   레지스트리의 escalate_if 충족
-   추가 질문 3회 후에도 분류 실패
-   고객이 "상담원 연결"을 직접 요청
-   강한 부정 감정 감지
-   개인정보를 포함하지 않고 상담원에게 전달할 수 있는 요청에 한해 이관

**핸드오프 패키지 (티켓 본문)**

-   3줄 요약: 고객이 원하는 것, 확인된 정보, 시도한 해결책
-   분류 결과와 확신도, 감정 상태
-   개인 예매 정보를 조회해 티켓에 넣지 않음. 필요할 경우 사용자가 자발적으로 제공한 내용도 공개 데모의 개인정보 정책에 따라 최소화·마스킹
-   추천 다음 조치

고객에게는 "상담원에게 전달했다"는 안내와 티켓 번호를 주고, 필요하면 대체 방법을 함께 준다.

## 초기 데모 시나리오

네 개 시나리오로 자동화 수준 세 단계와 이관을 모두 보여준다.

| # | 고객 메시지 | 처리 흐름 | 보여주는 것 |
| --- | --- | --- | --- |
| 1 | 공연 10분 전인데 QR이 안 떠요 | 긴급도 상 → 대체 입장 방법 먼저 안내 → 현장 알림 → 트러블슈팅 | 기술지원 + 서비스 연속성 |
| 2 | 다음 주 토요일 공연 주차 돼요? | 일반 정보 → RAG → 즉시 답변 | 자동 답변 |
| 3 | 어제 예매한 거 취소할게요 | 초기 계획: 본인 조회·견적·확인 후 티켓. 현재는 개인 기록이 필요하므로 요청을 제한 | 과거 설계 이력; 현재 제공 기능 아님 |
| 4 | 두 번 결제됐는데 진짜 짜증나네요 | 초기 계획: 예매 조회 + 부정 감정 이관. 현재는 개인 예매 조회 없이 일반 안내·개인정보 없는 이관 | 개인정보 없는 부분만 현재 범위 |

**발표용 보너스 데모**: 레지스트리에 새 업무 항목(예: 양도 문의)을 추가하고 서브워크플로우를 연결하면 코드 수정 없이 분류·처리되는 모습을 보여준다.

## MVP 범위와 단계

아래 MVP는 초기 기획 기준을 보존한다. 최신 통과 수치는 실행 결과서 T행을 본다.

| 구분 | 포함 항목 |
| --- | --- |
| 필수 (초기 기획) | 공통 Webhook 계약, 기술 장애·결제 오류·예매 조회·환불 안내·일반 정보 + 보완 질문·이관, `knowledge/`, `data/users.json`·`records.json`, In-Memory RAG, 데이터 API 티켓·알림·로그. 예매 조회와 개인별 환불은 현재 제공하지 않음 |
| 가산 | 웹 채팅 위젯, 상담원 콘솔, 실제 Slack, 실제 취소 API, PGVector(Supabase), 복합 의도 처리, 레지스트리 라이브 데모 |
| 제외 | 실제 결제 연동, 음성 채널, 다국어 |

**단계 (80~82일차, 마감 11/09 14:50)**

1.  설계: 업무 레지스트리, 데이터(`users.json`·`records.json`), 지식 문서 6개, 공통 시나리오 옮기기
2.  골격: ticketmoa-support + 입력 검사 + 하위 웹훅 껍데기 연결 (400·차단 통과)
3.  업무 확장 (초기 일정): ticketmoa-agents, ticketmoa-search, ticketmoa-tech, ticketmoa-payment, ticketmoa-refund(당시 계획은 2단계 확인 포함)로 데모 시나리오 1~3 동작. 개인 조회·환불 처리는 현행 범위에서 미제공
4.  이관·예외: ticketmoa-handoff, 감정 감지, 재시도·DLQ·중복, ticketmoa-errors로 데모 시나리오 4와 장애 시나리오 동작
5.  시험·문서: 공통 14 + 팀 5개 × 3회, 설계서 2종과 실행 결과서, 가산 화면

## 평가 지표

공통 시나리오 14개와 팀 시나리오 5개 이상을 3회씩 돌려 숫자로 보고하고, 여유가 있으면 테스트 문의 50~100개로 분류 정확도를 잰다.

| 지표 | 측정 방법 | 목표치 (안) |
| --- | --- | --- |
| 공통 시나리오 통과 | 14유형 × 3회 | 전부 통과 |
| 분류 정확도 | 예측 intent = 정답 intent 비율 | 90% 이상 |
| 자동 해결률 | 이관 없이 끝난 요청 비율 | 60% 이상 |
| 확인 없는 티켓 생성 (초기 환불 설계 지표) | 당시 개인별 환불 확인 흐름에서 고객 확인 없이 만들어진 환불 요청 티켓 | 0건; 현재 개인별 환불 티켓 흐름은 제공하지 않음 |
| 적절한 이관률 | 이관해야 할 건을 실제로 이관한 비율 | 95% 이상 |
| 답변 근거율 | RAG 근거가 있는 답변 비율 | 95% 이상 |

테스트셋에는 오타, 줄임말, 복합 의도, 감정 섞인 문장을 일부러 넣어 실제 고객 말투에 가깝게 만든다.
