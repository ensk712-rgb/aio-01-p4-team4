1. 전체 작동 과정

웹앱이 유일한 입구다. 본체 ticketmoa-support 가 규칙 검사와 경로 결정을 맡고, 하위 웹훅 9개가 분류·검색·답변·조회·환불·이관을 나눠 한다. 모든 호출은 HTTP 웹훅(X-Team-Key)이고 티켓은 ticketmoa-handoff 한 곳에서만 만든다.

웹앱요청 작성·프리셋→ support ① 검사400 · 주입 · 레이트리밋 · IP→ support ② 중복/cache · /tickets-created→ agentsSupervisor 분류 (LLM)→ search ∥ payment권한별 검색 · 본인 건 조회→ tech / refund작성·검증 (LLM) · 환불 계산→ handoff티켓 · 재시도 · DLQ · 알림→ support ③ 응답9칸 조립 · 가림 · /logs
단계판정 주체무엇을 하나실패하면
① 입력 검사·앞단 규칙Code (규칙)빈 질문·없는 사용자·501자 → 400. 주입 문구·60초 5회 초과·해외/블랙리스트 IP → 차단. 시간 예산(7.5초) 생성사용자 목록 조회 실패는 400 이 아니라 이관
② 중복 확인Code + /cache + /tickets-created같은 request_id 면 본인 재전송은 같은 응답 재생(duplicate), 타인이면 400 request_id_conflictcache 조회 실패면 새 요청으로 진행, 티켓 key 멱등성이 뒤를 막음
③ 빠른 길 / 분류Code → agents(LLM)C-번호 상태 질문은 LLM 없이 조회. 아니면 Supervisor 가 intents·entities·sentiment·urgency·confidence·clarity JSON 출력JSON 못 읽음·timeout → 담당자 이관
④ 경로 결정Code (decideRoute)모호 → 보완 질문(3회째 이관). 결제 오류·암표·강한 불만·상담원 요청·당일 취소 → 이관. 스태프 절차 → 권한 확인—
⑤ 검색 ∥ 조회search(임베딩) · payment(API)access_level 에 맞는 메모리 키로만 검색, 점수 0.42 미만 제외. 본인 건만 조회(403 → 권한 없음), 연락처 가림색인 없음 → indexed:false 로 구분. 조회 timeout 2.5초 → lookup_error
⑥ 답변·검증tech(LLM 2회) · refund(규칙)근거 안에서 작성 → 규칙 검사(grounded·자백 문구·스태프 용어) → 검증 Agent relevant·grounded·policy_ok. 환불은 수수료·환불액 계산 후 2단계 확인검증 실패·근거 없음·시간 부족 → 이관
⑦ 이관handoff(API)key=request_id 로 티켓. 429·5xx·timeout 만 재시도. 예산 소진 → DLQ + 알림 + ticket nullHTTP 200 + 담당자 이관으로 닫음(500 없음)
⑧ 응답·기록Code계약 9칸 조립, 연락처 가림(masked), 응답 뒤 /logs 기록(원문·연락처 없음, channel 정규화)Error Trigger → /alerts

3. 미구현·부분 구현 범위

이 MVP 는 과제 고정 스택(n8n + 연습용 데이터 API + In-Memory Vector Store) 위에서 동작한다. 아래 항목은 구현하지 않았거나 일부만 했다. "범위 밖(의도)" 는 정책상 일부러 하지 않은 것이다.
항목상태현재 동작이유·대안
영속 데이터베이스미구현티켓·캐시·실행 기록·DLQ·알림이 모두 연습용 데이터 API(server.py)의 메모리에 있다. 컨테이너를 재시작하면 사라진다. PostgreSQL·Supabase 같은 DB 연동 없음.과제 스택이 연습용 API 로 고정(AGENTS §2). 실서비스라면 티켓·로그 테이블과 멱등 키 인덱스가 필요하다.
벡터 저장소 영속성미구현In-Memory Vector Store 라 n8n 이 재시작되면 색인이 사라져 ticketmoa-index 를 다시 돌려야 한다. 검색은 색인 전이면 indexed:false 로 알린다.고정 스택. 실서비스는 pgvector·Qdrant 등.
실제 환불·결제 취소 실행범위 밖(의도)환불 금액 계산과 2단계 확인까지만 하고 실행은 티켓으로 상담원에게 넘긴다.정책상 에이전트가 돈을 움직이지 않는다(AGENTS §5).
실제 알림 채널·업무 도구미구현Slack·이메일·SMS·Jira 연동 없음. 알림과 티켓은 데이터 API 의 /alerts, /tickets 에 기록될 뿐 사람에게 전달되지 않는다.AGENTS §2 가 금지. 가산 여부는 리드가 정한다.
사용자 인증·세션미구현요청의 user 이름으로 사용자 목록을 조회할 뿐 로그인·토큰이 없다. 웹앱에도 로그인이 없어 SSH 터널(127.0.0.1)로만 연다.시연 범위. 실서비스는 OAuth/세션과 요청자 검증이 필요하다.
대화 상태 서버 보관부분 구현attempt 와 이전 질문은 클라이언트(웹앱)가 context 로 보낸다. 서버는 attempt 값을 신뢰한다. 환불 대기 상태만 서버(/cache)에 둔다.서버 카운트는 --repeat 시험과 충돌. 실서비스는 대화 세션 저장소가 필요하다.
예매번호(booking_id)로 조회부분 구현데이터 API 가 C-번호(record_id)만 받는다. 환불 2차는 1차에서 저장한 record_id 로 재조회해 우회한다.API 한계. booking_id 인덱스가 있는 DB 가 있으면 직접 조회.
