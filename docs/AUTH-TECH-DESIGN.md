# TicketMoa 사용자 인증 및 권한 관리 기술 설계

> 상태: **과거 상용화 확장 제안, 현재 프로젝트 범위에서는 비활성** · 작성 기준: 2026-11-06 저장소 파일과 사용자 제공 VM 확인 결과  
> 범위: 웹앱의 개인별 인증, Support의 신원·권한 검증, Search의 직원 전용 검색 경계, 개인 기록·환불 접근 제어

**현재 프로젝트의 확정 범위는 로그인 없는 공개 기술지원 자동화 시연이다.** 회원가입·로그인·세션·개인 토큰 및 사용자 인증 시스템은 의도적으로 구현 범위에서 제외했으며, 프로젝트의 필수 미완료 항목이 아니다. 아래 내용은 향후 상용 서비스 확장을 검토할 때 참고할 수 있도록 보존한 과거 제안이며, 현재 구현 계획이나 완료 기준으로 사용하지 않는다. 수업 시나리오의 본인 문의 조회는 요청 `user`와 기록 `requester`의 일치로만 판단하므로 사칭을 막지 못한다. 가짜 데이터로 한 시연의 한계이며, 실제 데이터를 다루려면 이 문서의 인증이 먼저 필요하다. 현재 Search의 직원 검색 차단은 공개 시연 정책으로 유지한다. `X-Team-Key`는 서비스 간 호출 인증일 뿐 개인 신원을 증명하지 않는다. RAG 구조와 측정값은 [RAG 설계서](RAG-ARCHITECTURE.md), 현재 실행 결과는 [실행 결과서](EXECUTION-RESULT.md)를 따른다.

## 1. 목적 및 적용 범위

**과거 제안의 목적:** 요청자가 적은 이름으로 직원 권한이나 타인 기록 접근 권한을 얻지 못하게 하고, 확인된 `user_id`로 `/employees`의 권한을 조회하는 방안을 설계한다. 이 문서는 실제 로그인·인증 구축 지시가 아니다. 현재 프로젝트는 미로그인 공개 기술지원을 목표로 하며, 직원 검색은 차단하고 개인 문의·결제·환불 상태 기능은 비로그인 정책에 맞게 별도로 제한해야 한다. 향후 상용화 범위가 승인될 경우에만 이 제안의 인증·소유권 설계를 다시 검토한다.

| 항목 | 현재 코드 상태 (2026-11-06 확인) | 과거 제안 목표 (현재 범위 밖) |
| --- | --- | --- |
| 사용자 식별 | 웹앱이 브라우저의 `user` 이름을 전달하고 Support `Check input`이 같은 이름의 `/employees` 레코드를 선택 | 웹앱이 개인별 증명을 확인하고 Support가 검증된 `user_id`로 레코드를 선택 |
| 사용자 데이터 | `data/users.json`에 5명(고객 4·직원 1)의 `usr-0001`~`usr-0005`가 있음. VM `/employees`의 5개 ID 반환은 사용자 확인 결과 | ID의 중복·누락을 배포 시 재확인하고 ID를 권한 매핑의 키로 사용 |
| 웹앱 인증 | `/api/chat`에는 사용자 세션 검사 없음. 관리자 Basic 인증은 관리자 경로만 보호 | 직원 및 개인 데이터 요청에 사용자 세션 적용. 익명 요청은 공개 검색으로 제한 |
| Support 인증 | `Question webhook`의 `X-Team-Key` Header Auth만 적용 | 팀 키에 더해 사용자 assertion을 별도 검증. 역할은 `/employees`에서 조회 |
| Search | `검색 준비`가 `search_staff=false`로 직원 검색을 전면 차단 | 공개 경로는 고객 인덱스만, 별도 내부 인증 경로는 확인된 직원에 한해 두 인덱스 검색 |
| 시험 | 이전 버전의 공통 17/17 및 SEC-01·02 2/2 기록이 있음 | 새 인증 버전의 독립 회귀·위조·직원 양성 시험을 새 원본으로 기록 |

## 2. 현재 시스템 구조와 보안 문제

- [웹앱](../webapp/app.py)의 `build_request`는 `payload.user`를 그대로 공통 요청의 `user`로 만든다. [화면](../webapp/static/app.js)은 `/api/config`의 사용자 목록을 선택지로 보여 주고 선택한 이름을 `/api/chat`에 보낸다. `/api/config`는 현재 전체 사용자 레코드도 내려준다.
- 웹앱의 `TM_ADMIN_PASSWORD` Basic 인증은 `/admin`, `/demo`, `/api/admin/*`에 적용된다. 일반 `/api/chat`의 신원 확인 수단이 아니다. 웹앱 서버만 알고 있는 팀 키를 Support에 붙이지만, 이는 모든 사용자에게 같은 서비스 키다.
- [Support](../workflows/ticketmoa-support.json)의 `Get users`는 `http://data-api:8800/employees`를 읽고 `Check input`은 `u.name === b.user`로 사용자를 고른다. 이 레코드의 `access_level`이 검색·답변 경로로 전달된다. `lib/common.js`의 `validateRequest`도 이름 기준이다.
- [Search](../workflows/ticketmoa-search.json)의 공개 웹훅은 팀 키를 사용한다. `검색 준비`가 `access_level: staff` 요청을 차단하고 `search_staff=false`를 고정하므로 정상 직원 검색도 현재 불가능하다.
- [Payment](../workflows/ticketmoa-payment.json)는 Support가 전달한 `user`를 데이터 API의 `requester`로 보낸다. 데이터 API의 소유권 비교만으로는 최초 요청자가 그 이름의 실제 소유자인지 증명할 수 없다. 환불·티켓 생성에서도 요청자의 신원과 대상 기록의 소유권을 구분해 검증해야 한다.

## 3. 사용자 인증 정책 및 권한 모델

| 확인된 신원 | 공개 지식 | 직원 지식 | 개인 기록·환불 | 처리 원칙 |
| --- | --- | --- | --- | --- |
| 미인증 | 허용 | 거부 | 거부 | 요청의 `user`, `user_id`, `access_level`은 권한 근거가 아님 |
| 인증된 `all` 사용자 | 허용 | 거부 | 본인 소유 건만 허용 | 역할은 `/employees` 조회 결과에서 결정 |
| 인증된 `staff` 사용자 | 허용 | 허용 | 본인 소유 건만 허용 | 직원 권한은 타인의 예매·문의 소유권을 대신하지 않음 |

클라이언트가 보내는 이름·ID·역할은 표시 또는 호환 입력일 뿐이다. 인증된 신원과 이름이 다르면 요청을 거절한다. 인증 데이터 누락은 공개 기능에만 허용한다. **제출된 인증정보가 유효하지 않은 경우**에는 공개 권한으로 조용히 낮추지 않고 인증 오류를 반환한다. 역할·소유권 판단은 LLM에 위임하지 않는다.

## 4. 웹앱 로그인·세션 설계

**목표:** 기존 웹앱 백엔드에 토큰 입력·세션 발급 경로를 추가한다. 이것은 아직 존재하지 않는 API다.

1. 직원과 개인 기록 기능을 쓰는 고객은 서버가 사전에 발급한 개인별 불투명 Bearer 토큰을 HTTPS로 한 번 제출한다. 화면은 토큰을 `localStorage`, URL, 채팅 본문에 저장하지 않는다.
2. 웹앱 서버가 토큰을 검증해 `user_id`를 얻고 충분히 긴 난수 세션 ID를 발급한다. 서버 메모리에는 세션 ID의 해시, `user_id`, 토큰 식별자, 만료 시각을 보관한다. 브라우저에는 `HttpOnly`, `Secure`, `SameSite` 쿠키만 보낸다. 서버 재시작 시 메모리 세션은 사라져 재인증한다.
3. `/api/chat`은 세션을 확인한 뒤 인증된 ID의 이름을 서버에서 결정한다. 브라우저의 사용자 선택값이 다르면 거절한다. 익명 채팅은 공개 정보 질문만 처리하며 개인 기록·환불·본인 명의 티켓 경로로 보내지 않는다.
4. 쿠키 기반 요청에는 `Origin` 확인과 CSRF 방어를 둔다. 세션 만료·로그아웃·토큰 폐기 시 해당 세션을 지운다. `TM_TARGET=vm`으로 로컬 PC에서 시연하는 구성은 신뢰된 중앙 인증 서버로 간주하지 않는다.

토큰·서명 키를 가진 웹앱 프로세스는 **신뢰된 서버**에서 실행해야 한다. 현재 기본 실행 위치는 사용자 PC의 `127.0.0.1:8080`이며, 중앙 웹앱의 VM 배포·HTTPS·접근 경로는 아직 구축됐다는 근거가 없다. 이 배치가 확정되기 전에는 로컬 시연 웹앱이 만든 assertion으로 운영 직원 권한을 열지 않는다.

## 5. 사용자별 토큰 발급·검증·폐기

**제안:** 사용자마다 예측 불가능한 256비트 이상 난수 토큰을 오프라인 관리자가 발급한다. 원문은 발급 시 한 번만 안전한 경로로 전달한다. 서버의 저장소에는 토큰 해시와 `user_id`, 상태·발급·만료 시각만 둔다. 이 저장소는 Git·워크플로우 JSON·브라우저에 넣지 않는 접근 제한 파일 또는 기존 서버 비밀 관리 방식으로 마련하며, 실제 위치·백업·담당은 배포 전 결정한다. `users.json`의 ID 자체는 토큰이 아니다.

로그인 요청에서는 해시를 일정 시간 비교 방식으로 확인하고, 만료·폐기된 토큰은 거부한다. 분실·퇴사 시 토큰을 폐기하고 관련 세션도 무효화한다. 토큰 교체에는 일정 기간의 중복 유효 여부를 정책으로 정한다. 관리자 Basic 비밀번호와 `X-Team-Key`를 개인 토큰으로 재사용하지 않는다. 인증 요청 횟수 제한 및 실패 로그에는 계정·토큰 원문을 남기지 않는다. **발급 도구·토큰 레지스트리·폐기 경로는 미구현**이다.

## 6. 인증 검증 서비스 배포 위치 및 접근 경로

**추천 배치:** 신뢰된 웹앱 백엔드를 팀 VM에 배치하고, n8n이 이미 `data-api:8800`으로 접근하는 **기존 연습용 데이터 API 서비스**에 내부 assertion 검증 기능을 추가한다. 별도 DB·외부 인증 사업자는 도입하지 않는다. 웹앱은 브라우저의 개인 토큰을 확인하고 assertion을 서명한다. Support는 기존 데이터 API 네트워크의 내부 검증 경로를 호출해 서명 결과를 받는다. 검증 API는 서비스 전용 Credential로 보호하고 외부에 공개하지 않는다. 기존 `X-Api-Key`나 `X-Team-Key`만으로 사용자 역할을 부여하지 않는다.

| 경계 | 제안 계약 | 실패 처리 |
| --- | --- | --- |
| 브라우저 → 웹앱 | HTTPS 토큰 교환, 이후 세션 쿠키 | 잘못된 토큰 401, 세션 미인증은 공개 기능만 |
| 웹앱 → Support | 기존 `POST /webhook/ticketmoa-support` 본문과 팀 키 유지, 별도 서명 assertion 헤더 추가 | assertion 전송 실패 시 직원·개인정보 처리 금지 |
| Support → VM 내부 검증 서비스 | **제안** `POST /auth/verify-assertion`에 assertion·요청 ID 전달, 서비스 Credential 사용 | 타임아웃·401·403·5xx·오류 본문은 모두 권한 미확인으로 처리, 해당 경로 재시도 금지 |
| Support → `/employees` | 검증된 `user_id`를 반환된 5개 레코드와 대조 | 조회 실패·ID 중복·누락 시 직원·개인정보 처리 금지 |

`/auth/verify-assertion`은 **현재 존재한다고 확인된 API가 아니다**. 데이터 API 구현은 이 저장소에 없으므로 D 담당이 원본 소스, 확장 허용 여부, 내부 URL·Credential·타임아웃을 확인해야 한다. 팀 `AGENTS.md`는 외부 서비스를 연습용 데이터 API로 제한한다. 이 확장이 불가능하면 별도 내부 검증 서비스 또는 n8n 내 안전한 서명 검증 방식에 대해 리드 승인을 먼저 받아야 하며, 그 전까지 직원 검색 차단을 유지한다. 사용자 PC의 `localhost`를 VM에서 접근 가능한 검증 서비스로 가정하지 않는다.

## 7. 웹앱 → Support 서명된 신원 정보 전달

**제안 형식:** 서명 알고리즘을 고정한 HMAC-SHA-256 assertion을 별도 헤더에 넣는다. 페이로드는 `sub`(확인된 `user_id`), `aud`(`ticketmoa-support`), `iat`, `exp`(발급 후 최대 30초), `request_id`, `jti`(일회용 난수), 발급자 식별자만 포함한다. `access_level`을 넣더라도 최종 권한의 근거로 사용하지 않는다. 서명 키는 팀 키·개인 토큰 키와 분리하고 인증된 웹앱 서버와 검증 서비스의 비밀 설정에만 둔다.

VM 검증 서비스는 서명 알고리즘 고정, 서명 일정 시간 비교, 발급·만료 시각과 허용 시간 오차, `aud`, `request_id`, `jti`의 최초 사용을 검사한다. 재사용 방지에는 **원자적 일회성 `jti` 기록**이 필요하다. 기존 `/cache`가 원자적 소비를 지원하는지는 확인되지 않았으므로 기능이 검증되기 전에는 완전한 재사용 차단을 주장하지 않는다. TTL만 짧게 두는 것은 위험을 줄일 뿐이다. 원문 assertion을 본문·응답·로그에 복사하지 않는다.

## 8. Support의 user_id 기반 사용자·권한 확인

**제안 흐름:** `Question webhook` → 서명 검증 요청 → `Get users` → `Check input` → 기존 `Valid?` 및 업무 분기. 인증정보가 아예 없는 공개 요청과 **제출했으나 검증 실패한 요청**을 구별한다.

1. 검증 서비스가 서명·만료·audience·요청 ID·재사용을 통과한 `user_id`만 Support에 반환한다. Support는 클라이언트 본문의 `user_id`나 `access_level`을 무시한다.
2. `Get users`의 `/employees` 결과에서 ID가 정확히 하나인 레코드를 찾고 `name`, `access_level`을 서버 측 값으로 확정한다. 인증된 ID와 본문의 `user` 이름이 다르면 위조 시도로 거부한다. 직원 역할과 개인 기록 소유권은 별도 검사한다.
3. 공개 요청은 직원 여부를 조회해 승격하지 않는다. 개인 기록·환불·본인 명의 티켓 생성 경로는 인증 없이는 닫는다. 서명 검증이나 `/employees` 조회 실패 시 직원·개인정보 경로는 닫는다.
4. 공통 계약의 400 입력 오류(빈 질문·없는 사용자·501자)는 유지한다. 인증 실패의 HTTP 상태·응답 코드는 A 리드가 공통 계약과 시험 도구에 맞춰 확정한다. 인증 실패를 일반 400 입력 오류 또는 성공 응답으로 위장하지 않는다.

`Check input`의 원본 함수가 `lib/common.js`에 있으므로 A 담당은 그 함수를 먼저 수정하고 기존 단위 시험을 확인한 뒤 워크플로우 Code 노드에 동일한 코드를 반영한다. 모든 후속 노드는 **확정된 사용자 레코드**를 사용해야 하며, `Call tech`, `Call payment`, `Call refund`, `Call handoff`의 사용자·권한 전달도 함께 점검한다. 새로운 검증 노드의 유형·버전은 `AGENTS.md`의 실습 reference 규칙을 따른다.

## 9. Search의 공개·직원 전용 경로 분리

| 경로 | 인증·권한 | 저장소 | 현재/목표 |
| --- | --- | --- | --- |
| `ticketmoa-search` 공개 경로 | 기존 팀 키는 서비스 호출만 확인. 본문의 `access_level: staff`는 무시 또는 거부 | `ticketmoa_kb_v1_all`만 | 현재 직원 요청 차단 유지 |
| **제안** `ticketmoa-search-internal` | 별도 서비스 Credential을 가진 Support 내부 호출만. Support가 검증된 `staff` 레코드를 확인한 뒤 호출 | 고객용 `ticketmoa_kb_v1_all` + 직원용 `ticketmoa_kb_v1_staff` | 미구현, 별도 경로·Credential·시험 필요 |

C 담당은 공개 웹훅 `검색 요청 수신`·`검색 준비`의 고객용 동작을 유지하고, 별도 내부 Webhook/검증 분기로 기존 `스태프 저장소 검색`을 재사용한다. A 담당은 `Call search`, `Call search ∥`, `Call search (evidence)`의 분기를 맞춘다. 내부 Credential 보유 자체를 사용자 신원으로 취급하지 않고, Support의 검증 완료 결과가 있어야 내부 경로를 호출한다. 직접 Search 호출·직원 역할 본문 조작은 직원 인덱스를 실행하지 않아야 한다. 새 하위 웹훅 경로·계약은 `AGENTS.md`와 `docs/IMPLEMENTATION-PLAN.md`에 따라 리드 합의가 필요하다.

## 10. 비밀키 관리, 토큰 만료·재사용 방지, 로그 보호

비밀은 사용자 토큰, 세션 ID, assertion 서명 키, 내부 검증 Credential, 내부 Search Credential, 기존 `X-Team-Key`로 분리한다. 실제 값은 저장소·문서·워크플로우 JSON에 기록하지 않는다. 인증 실패 시 서명 원문·토큰 원문·쿠키 값을 오류 메시지에 넣지 않는다. 만료된 토큰·세션·assertion은 거부하며 401·403은 재시도하지 않는다.

| 노출 경로 | 구현 시 보호 기준 |
| --- | --- |
| 브라우저 저장소·응답 | 토큰은 로그인 제출 뒤 JS 메모리에서 제거; `localStorage` 금지. `/api/config`는 전체 사용자 레코드 대신 공개 표시 정보만 제공. `/api/chat`의 `request` 응답에 비밀 필드 금지 |
| 웹앱 대화 기록·서버 로그 | `ChatLog.add` 전에 인증 헤더·쿠키·assertion을 제거. 현재 전화·이메일 가림 규칙은 인증정보 제거를 대체하지 못함 |
| n8n 실행 기록 | assertion을 본문으로 복사하지 않고 필요한 검증 결과(`user_id`, 검증 상태)만 후속 노드에 전달. Webhook 원본 헤더·실행 데이터 보관 정책과 접근 권한은 VM에서 별도 확인 |
| 오류·시험 결과 | 실패 코드·요청 ID·익명화된 사용자 ID만 남김. 토큰·서명·세션·Credential 값은 출력·보고서에 기록 금지 |

키 교체 시 웹앱 서명 키와 검증 서비스 키를 동기화하고 이전 키의 폐기 시점을 기록한다. 지원 환경에 안전한 비밀 배포·회전 절차가 없으면 직원 경로를 열지 않는다.

## 11. 개인 문의 조회 및 환불 관련 접근 제어

- 공개 정책 문서 안내와 본인 예매·문의 상태 조회를 분리한다. 기록 조회에는 인증된 `user_id`에서 얻은 정식 `name`을 Payment의 `requester`로 사용하고, 데이터 API 응답의 소유자도 다시 확인한다. 본문의 다른 사람 이름으로 `requester`를 바꾸지 않는다.
- 환불 규정 검색은 공개 기능일 수 있지만 **개별 예매 금액·견적·확인·티켓 생성**에는 인증된 ID와 대상 기록 소유권을 요구한다. `context.confirm=true`는 환불 요청 의사 표시이지 신원 증명이 아니다. 기존 환불 2단계 규칙과 중복 방지 키는 유지한다.
- 인증 오류·소유권 불일치·조회 장애에서는 금액과 연락처를 공개하지 않는다. 직원 역할도 다른 고객의 기록 접근을 자동 허용하지 않는다. Payment·Refund·Handoff가 직접 호출되는 경로는 서비스 인증과 검증된 신원 전달 계약을 별도로 점검한다.

## 12. 기존·신규 테스트 계획 및 판정 기준

[공통 17개](../cases/common.json)는 모두 공개 검색 시험이 아니다. 아래 분류는 **인증 필요성의 설계 판정**이며 기존 기대값을 바꾸거나 새 버전 통과를 뜻하지 않는다.

| 분류 | 공통 케이스 | 인증 버전에서 필요한 조치 |
| --- | --- | --- |
| 공개 질문·입력 검사 | WF-01, WF-02, WF-05, WF-08, WF-10, WF-13 세 케이스 | 익명 공개 경로 유지. WF-10이 이관·티켓으로 이어지는 경우 사용자 귀속 처리도 확인 |
| 본인/타인 기록 조회 | WF-06, WF-07, WF-11, WF-12 | 검증된 요청자 ID를 별도 인증정보로 제공. WF-06은 인증된 박서준이 타인 기록을 조회해도 거절 |
| 사용자 귀속 티켓·중복 | WF-02b, WF-03, WF-04, WF-09 두 케이스 | 검증된 요청자 ID 제공. WF-09 두 요청의 동일 `request_id` 유지 |
| 환불·금액·확인 | 공통 17개에는 직접 해당 없음. [팀 케이스](../cases/team.json)의 TM-02·03·06·13 등 | 인증된 소유자와 예매 기록 대조, 기존 확인·금액·이관 규칙 유지 |

기존 `cases/common.json`의 본문·기대값과 [SEC-01·02](../cases/security-permissions.json)의 과거 통과 이력은 보존한다. 현재 `tools/flow.py`는 `X-Team-Key`만 자동 첨부한다. 새 인증 버전의 보호 기능을 시험하려면 E 담당 테스트 호출기가 **환경변수나 비밀 설정에서 케이스별 사용자 인증정보를 읽어 헤더로 주입**하도록 별도 설계해야 한다. 토큰을 케이스 JSON에 넣지 않는다. 익명 공개 시험과 인증된 고객 시험을 분리하고, 기존 17/17·2/2를 새 버전 통과로 재사용하지 않는다.

추가 음성 시험: 다른 직원 이름, 임의 `user_id`, `access_level: staff`, 잘못된 서명, 만료·잘못된 audience·다른 `request_id`, 재사용 `jti`, 인증 누락, 검증 서비스 장애·타임아웃, 팀 키만 가진 직접 Support/Search 호출, 고객의 타인 기록·환불 접근. 양성 시험: 익명 공개 검색, 인증 고객의 본인 기록·환불, 인증 직원의 공개+직원 문서 검색. Search 직접 호출로 직원 문서가 노출되면 실패다. 최종 공통 17개와 SEC-01·02는 **변경 후 버전에서 새로 실행**하고, WF-01 8초·WF-11 6초 경계 및 추가 인증 호출의 지연도 확인한다.

**최종 수용 기준:** 서명 검증 또는 `/employees` 조회가 실패하면 직원·개인정보 경로는 닫힌다. Search 임시 차단은 인증된 직원의 양성 시험과 고객 위조·직접 호출 음성 시험이 통과한 뒤에만 해제한다. 익명 공개 검색, 본인 기록·환불 소유권, 기존 공통·보안 회귀도 별도로 통과해야 한다.

## 13. 과거 제안: 구현·배포·검증·롤백 순서

아래 단계는 현재 프로젝트의 할 일 목록이 아니다. 향후 제품 범위가 로그인과 직원 검색을 포함하도록 공식 변경되는 경우에만 재검토한다.

1. **계약·담당 결정:** 리드가 공통 요청/응답의 인증 실패 상태, 내부 Search 경로, 테스트 신원 주입 방식을 승인한다. D는 `/employees` ID의 유일성과 검증 API 확장 가능성, VM 배치·내부 접근 경로를 확인한다. 현재 5개 ID 반환은 사용자 제공 VM 확인 결과이며 상세 API 구현은 저장소 밖이다.
2. **비밀·검증 기반:** VM의 신뢰된 웹앱 배치, HTTPS, 토큰 레지스트리·세션 보관, 데이터 API assertion 검증, 별도 서비스 Credential과 재사용 방지 저장소를 준비한다. 비밀 값을 Git에 넣지 않는다.
3. **웹앱·Support:** 웹앱에서 토큰·세션·서명을 구현한다. A가 `lib/common.js` 원본과 Support `Check input` 및 모든 사용자 전달 경로를 수정한다. 이 단계에서도 Search 직원 차단을 유지한다.
4. **공개·개인정보 회귀:** 익명 공개, 인증 고객의 본인 조회·환불, 고객 위조, 검증 서비스 장애, 기존 17개와 SEC-01·02를 새 버전에서 시험한다. 실패 시 인증 경로를 우회해 이름 기반 권한으로 되돌리지 않는다.
5. **직원 경로:** C가 별도 내부 Search 경로·Credential을 추가하고 A가 검증된 직원 분기만 연결한다. 고객 직접 호출 차단과 직원 양성 시험을 각각 실행 ID·배포 해시와 연결해 기록한다. 모두 통과하기 전에는 임시 패치를 해제하지 않는다.
6. **배포·복구:** 각 담당 파일만 VM에 반영하고 리드가 공용 버전을 취합한다. 배포 전후 워크플로우·데이터 해시와 Credential 존재 여부를 확인한다. 직원 경로 실패 시 내부 경로를 비활성화하고 공개 경로의 직원 차단을 유지한다. 키 유출·서명 검증 오류 시 관련 키와 세션을 폐기한다. 기존 이름 기반 직원 승격으로 롤백하지 않는다.

모든 배포·재시험은 팀 VM 사용 시점을 조율한 뒤 수행한다. 이 문서는 배포 완료나 테스트 통과를 주장하지 않는다.

## 14. 과거 제안의 미결정 사항 및 상용화 전 재검토 항목

표의 항목은 현재 프로젝트에서 남은 구현 작업이 아니라, 인증 기능을 별도 승인해 도입할 경우 다시 결정할 사항이다. 현재 데모의 사칭 한계는 결과서에 밝히고, 실제 개인 데이터를 넣지 않는다.

| 미결정·위험 | 결정·검증 조건 |
| --- | --- |
| 중앙 웹앱 배치 | 현재 로컬 시연 앱을 신뢰된 VM 서버로 배치할지, HTTPS와 브라우저 접근을 어떻게 제공할지 리드·운영 담당 결정 |
| 데이터 API 확장 | 원본 구현은 저장소에 없음. D가 `/auth/verify-assertion` 추가 허용, 내부 주소·Credential·timeout을 확인. 불가능하면 대안에 리드 승인 필요 |
| 단일 사용 보장 | 기존 캐시의 원자적 `jti` 소비 여부 미확인. 검증 불가 시 assertion 재사용 차단 완료로 주장하지 않음 |
| 인증 실패 계약 | 공통 웹훅의 기존 400 입력 오류와 별도 401/403 또는 권한 없음 응답을 어떻게 구분할지 A·리드 결정 |
| 기존 17개 호출 | 입력 본문을 유지하며 개인 인증 헤더를 주입할 시험 도구·비밀 공급 방식은 E와 결정. 현재 도구는 팀 키만 붙임 |
| VM 실행 데이터 | Webhook 원본 헤더 저장·열람·보존 정책, 관리자/팀원 접근 및 인증정보 제거 방식 확인 필요 |
| 지연·가용성 | 검증 호출이 WF-01 8초·WF-11 6초 기준에 미치는 영향, 서비스 중단 시 공개/보호 기능 분리 확인 필요 |
| 현재 Search 상태 | 임시 직원 차단 유지. 과거 직원 검색 양성 기록은 인증된 직원의 새 버전 통과 근거가 아님 |
| 문서·결과 담당 | `docs/AUTH-TECH-DESIGN.md`의 유지 담당은 팀 합의 필요. 기존 공식 시험 원본·실행 결과는 E 담당 `runs/`, `docs/EXECUTION-RESULT.md`에 보관 |

`docs/TEST-SUMMARY.md`는 현재 존재하지 않는다. 공식 테스트 결과의 원본은 기존 [실행 결과서](EXECUTION-RESULT.md)와 연결된 `runs/` 보고서로 유지하는 것을 권장한다. 별도 요약 문서가 필요하면 E 담당과 리드가 작성·관리 담당, 원본 링크, 중복 숫자 갱신 방식을 정한 뒤 생성한다. 이 설계서에는 실제로 실행하지 않은 신규 인증 시험의 통과 수치나 실행 ID를 넣지 않는다.
