## 새 결함과 남은 누출

### 1. 중간 · 거절된 타인 요청이 소유 cache를 바꿔 정상 재전송을 막음 [HTTP 재현]

- 김하늘의 고유 request_id로 T-2001 생성 → cache만 초기화 → 본인 재전송은 정상 → cache 초기화 → 박서준이 같은 ID 사용.
- 박서준은 이번 수정대로 티켓을 받지 못했다. 그러나 **그 뒤 김하늘이 원래 질문/ID로 재전송하면 400 request_id_conflict**가 됐다.
- support 「소유 기록」이 handoff 「중복 주인 판정」보다 먼저 박서준의 owner/fp를 저장하고, 거절 뒤에도 복원하지 않기 때문이다. `req:` 기록의 TTL은 하루다.
- **제안:** 실제 기존 티켓 소유권 확인 전에 소유 cache를 확정하지 않거나, 거절 때 검증된 원 소유자로 복구한다. 단순 거절만으로 잘못 쓴 cache가 남지 않게 해야 한다.

### 2. 높음 · 문자 접두어가 있는 연락처 channel은 여전히 로그에 남음 [HTTP 재현]

- 정상 상태 조회에 `channel:"web-010-0000-9901"`을 넣으면 `/logs`의 channel에 그대로 저장된다.
- 첫 글자 영문 제한도 이 값을 허용한다. AGENTS §6의 연락처 원문 금지는 순수 전화번호에만 적용되는 규칙이 아니다.
- **제안:** channel을 승인 enum으로 제한하거나, 네 기록 경로에 같은 개인정보 탐지/가림 정책을 적용한다. 기존 반례가 통과한 것은 순수 전화번호를 other로 바꿨기 때문이며, 이 추가 입력까지 해결된 것은 아니다.

### 3. 중간 · Ops의 잘못된 달력 날짜가 500 [HTTP 재현]

- `POST ticketmoa-ops {"from":"2026-99-99","to":"2026-99-99"}` → **500 `Error in workflow`**.
- 「기간 정리」의 정규식은 통과하지만, query_from 계산의 Invalid Date에 toISOString()을 호출한다.
- **제안:** 실제 달력 날짜와 from≤to를 검사해 구조화된 오류/정해진 기본값으로 처리한다. 사용자 입력으로 워크플로우 예외가 발생하지 않게 한다.

## 이 워크플로우 초안에 대해 남은 위험

- **위 3개는 현 스택에서 수정 가능한 문제**다. 특히 channel 누출은 개인정보 요구사항 미충족이다.
- `/tickets-created` 확인이 실패하면 정상 사용자의 중복 티켓도 숨기고 request_id_conflict로 안내한다. 비노출을 택한 fail-closed이나, 기술적 조회 불가와 실제 소유 충돌을 구분하지 못한다(코드 확인, HTTP 장애 주입 미실시).
- cache 소실 뒤 같은 사용자가 같은 ID를 다른 질문에 재사용하면, 티켓 API에는 원 지문이 없어 내용 일치까지 보장하지 못한다. 사용자/업무/지문의 내구 저장 규약이 필요하다.
- 동시 확정·소유 예약, 티켓 생성과 confirmed 저장의 원자성은 GET/POST cache와 현재 멱등 API만으로 보장되지 않는다.
- timeout 뒤 실제 티켓이 생길 수 있으며 DLQ와 공존한다. 같은 key로 수습해야 한다. 800ms 추가 예산도 전체 8초 보장이 아니다.
- 고정 In-Memory store 두 개의 원자 교체/영속성, 실제 환불 가능 상태와 상담 status의 구분, SDK 내부 재시도·실제 비용 계측은 여전히 제한적이다.
- mock과 현재 시나리오 통과는 실제 LLM 답변 품질·운영 부하·모든 오류 응답을 보증하지 않는다.

종료 시 fault 전부 ok/slow_seconds=8, mock ok/slow_seconds=8로 복원했다. 격리 API 초기화는 검증 중 사용했으며, n8n 재시작·재색인·재배포나 워크플로우 수정은 하지 않았다.
