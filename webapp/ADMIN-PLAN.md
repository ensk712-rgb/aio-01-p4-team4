# 관리자 페이지 계획 (2026-11-05, D 심환석)

> **진행 (11-05)**: 1·2·3·4단계 구현 완료 (`/admin`, `/demo`, `static/reasons.js`, `workflows/ticketmoa-ops.json`). 로컬에서 확인했고, VM에는 `ticketmoa-ops`를 아직 올리지 않았다. 5단계(상담원 답장)는 하지 않았다.

상담 채팅 웹앱(`webapp/`)과 같은 서버에 관리자 화면을 붙인다. 고객 화면에서 보낸 문의가 관리자 화면에 실시간으로 뜨고, 이관된 건은 티켓·알림(디스코드 포함)과 함께 보인다. 발표에서 고객 화면과 관리자 화면을 나란히 띄워 **고객 문의 → 워크플로우 → 담당자 쪽에서 보이는 것**을 한 흐름으로 보여 주는 것이 목표다.

## 1. 시연 시나리오 (이것이 되면 완성)

## 2. 범위

**한다**
- `/admin` 화면 하나: 대화 목록, 대화 상세(경로 재생 재사용), 장애 패널, 티켓·알림·DLQ, 보안 차단, 지표.
- 웹앱 서버가 지나간 모든 대화를 기록한다 (`webapp/var/chats.jsonl`, git 제외).
- 대상이 local이면 데이터 API를 직접, vm이면 n8n 웹훅 `ticketmoa-ops`를 거쳐 읽는다 (3장).

**하지 않는다**
- 환불 실제 실행, 티켓 상태 변경 (데이터 API에 그런 기능이 없고, AGENTS.md 5장의 "에이전트가 환불을 실행하지 않는다"를 지킨다)
- 로그인 체계. `127.0.0.1`에만 열고, 다른 곳에 열면 `TM_ADMIN_PASSWORD`를 둔다
- 디스코드 채널 읽기 (보낸 기록은 n8n 실행 결과로 본다)
- 장애 주입 (`/admin/fault`). VM에서는 장애가 이미 자주 난다 (아래 표). 일부러 만들지 않고 실제로 난 것을 보여 준다

### 실제로 나는 장애 (11-05 `runs/common-*` 최근 6회의 `reason` 집계)

| reason | 건수 | 뜻 | 장애 패널 분류 |
| --- | --- | --- | --- |
| `agents_failed` | 16 | 분류 에이전트 호출 실패·시간 초과 | 장애 · 분류 |
| `payment_failed` | 8 | 예매·문의 조회 실패 | 장애 · 조회 |
| `payment_error_handoff` | 14 | 결제 오류 문의 → 상담원 (설계대로) | 정상 |
| `writer_not_grounded` · `writer_staff_only_terms` | 8 · 4 | 작성 모델이 근거 없이 답함 / 직원 전용 용어 | 품질 · 작성 |
| `verification_failed` | 5 | 검증 모델이 답을 통과시키지 않음 | 품질 · 검증 |
| `llm_unavailable` | 6 | OpenAI 응답 없음 (WF-10 포함) | 장애 · LLM |
| `timeout_or_network` · `http_5xx` (handoff) | WF-04·11 | 티켓 API 실패 → DLQ·장애 알림 | 장애 · 티켓 |
| 그 밖 (`urgent_entry`, `not_owner`, `injection_pattern`, `clarify_limit_reached` …) | | 설계대로 이관·거절·차단 | 정상 (장애 아님) |

- 고객 화면에서는 모두 "담당자 이관"이라 구분이 안 된다. 관리자 화면은 `reason`과 `timings`를 보고 **설계대로 이관한 건**과 **장애 때문에 이관된 건**을 나눈다.
- 장애 패널: 최근 30분 장애 건수(분류별), 단계별 평균·최대 시간, 장애가 난 대화로 바로 가는 링크, errors 워크플로우 알림(`/alerts`의 `reason: unexpected`).
- 분류표(`reason` → 장애/품질/정상)는 `webapp/static/reasons.js` 한 곳에 두고 flow.js와 같이 쓴다. 새 `reason`이 나오면 "미분류"로 보이게 해 놓친 코드를 알 수 있게 한다.

## 3. 데이터 출처

VM의 데이터 API(8800)는 밖에서 접근할 수 없다. 밖에서 닿는 것은 n8n(https 5678)뿐이다. 그래서 대상별로 출처를 나눈다.

| 보여 줄 것 | local | vm |
| --- | --- | --- |
| 대화 (질문·응답·경로·시간) | 웹앱 기록 `chats.jsonl` | 같음 |
| 티켓 `GET /tickets-created` | 데이터 API 직접 (`X-Api-Key`) | `ticketmoa-ops` 웹훅 |
| 알림 `GET /alerts` · DLQ `GET /dlq` | 〃 | 〃 |
| 실행 기록 `GET /logs` (route별 건수) | 〃 | 〃 |
| 장애 스위치 상태 `GET /admin/fault` (읽기만) | 〃 | 〃 |

### `ticketmoa-ops` 워크플로우 (D 담당 파일, 가산)

AGENTS.md 4장에 이미 D 담당 가산 파일로 잡혀 있다. 79일차 Ops Assistant 예제를 복사해 읽기 전용 프록시로 만든다.

```
POST /webhook/ticketmoa-ops   (Header Auth: X-Team-Key)
요청 {"op": "tickets" | "alerts" | "dlq" | "logs" | "fault", "args": {...}}
응답 {"op", "data", "at"}   실패해도 HTTP 200 + {"error"}
```

- **읽기 전용**이다. `op`은 Switch로 화이트리스트만 받고, 데이터 API 경로를 요청에서 받지 않는다. VM 공용 상태를 바꾸는 호출은 없다.
- 응답에서 연락처는 `maskDeep`(lib/common.js)로 가린다.
- 79일차 Ops Assistant의 LLM 요약("오늘 이관 사유 요약")은 2단계에서 `op: "summary"`로 붙인다 (선택).

## 5. 웹앱 서버 API (추가분)

| 경로 | 동작 |
| --- | --- |
| `GET /admin` | 관리자 화면 |
| `GET /demo` | 고객 + 관리자 분할 화면 |
| `GET /api/admin/chats?since=<seq>` | `chats.jsonl`에서 새 대화만 (2초 폴링) |
| `GET /api/admin/chats/<request_id>` | 대화 한 건 (요청·응답·경로 원본) |
| `GET /api/admin/ops/<op>` | local: 데이터 API 직접 / vm: `ticketmoa-ops` |
| `POST /api/admin/reply` (선택) | 상담원 답장 저장 → 고객 화면이 `GET /api/chat/replies?user=`로 가져감 |
| `GET /api/admin/stats` | 대화 기록 + `/logs`로 지표 띠 계산 |

- `/api/chat`은 지금처럼 웹훅에 넘기고, 응답을 돌려주기 전에 `chats.jsonl`에 한 줄 쓴다 (`seq`, 시각, user, question, status, body, elapsed_ms). 질문과 답변의 연락처는 저장 전에 가린다.
- 팀 키·데이터 API 키는 지금처럼 서버 안에만 있다. `/api/admin/*` 응답에 키 값이 없는지 시험으로 확인한다.
- 바깥 주소(`TM_WEB_HOST`가 `127.0.0.1`이 아님)로 열 때 `TM_ADMIN_PASSWORD`가 없으면 시작을 거부한다.

| 단계 | 내용 | 파일 | 확인 |

| 1 | 대화 기록 + 관리자 화면 (대화 목록·상세·지표·장애 패널) | `webapp/app.py`, `webapp/static/admin.*`, `reasons.js` | 고객 화면 예시 6개 → 관리자 목록 6건, 장애/정상 분류가 맞음 |
| 2 | local 데이터 API 연동 (티켓·알림·DLQ·로그) | `webapp/app.py` | 로컬 시나리오 A·C |
| 3 | `ticketmoa-ops` 워크플로우 + vm 연동 | `workflows/ticketmoa-ops.json`, `webapp/app.py` | `flow.py check` 통과, VM에서 A·B·C·D |

- 같은 워크스페이스의 worker를 쓴다면 서버(`app.py`·시험)와 화면(`static/admin.*`)으로 나눈다. 5장의 API 표를 먼저 확정해 두 worker에 같이 준다.

## 8. 정해야 할 것

1. **`ticketmoa-ops`**: 읽기 전용으로 정했다 (장애 주입 없음). 가산 파일이라 리드(최두나)에게 시작해도 되는지 알린다.
2. **상담원 답장(E)**: n8n을 거치지 않는 웹앱 내부 기능이다. 발표에 넣을지 결정해야 한다.
3. **디스코드**: 관리자 화면에 "디스코드 전송됨"을 보이려면 handoff 응답에 전송 결과가 있어야 하는데, 지금은 응답을 보낸 뒤에 전송한다. 화면에는 `/alerts` 기록만 보이고, 디스코드는 발표 때 채널을 따로 띄워 보여 주는 쪽을 권한다.
4. **대화 기록 보관**: `webapp/var/`는 git에서 제외하고, 시연 전에 `rm webapp/var/chats.jsonl`로 비운다.
